# 5-minute venv migration checklist

## Why

The current `cypher/.venv/` lives inside `OneDrive-Personal/work/`, which means macOS's File Provider treats every `.so` and `.dylib` in the venv as a cloud-sync candidate. Under load it produces two failure modes:

- `mmap failed with errno=60` on `.so` imports (occasional, transient)
- `read()` hangs during module import that never recover (process must be killed)

Moving the venv to a non-synced path eliminates the entire class.

## Steps

Run each block in a fresh Terminal window. Total time: under 5 minutes.

### 1. Note what's currently installed (one-time)

From the project root, capture the dependency snapshot so the new venv matches:

```bash
cd "/Users/danielburke/Library/CloudStorage/OneDrive-Personal/work/cypher"
.venv/bin/pip freeze > /tmp/cypher_requirements.txt
echo "captured $(wc -l < /tmp/cypher_requirements.txt) packages"
```

### 2. Create the new venv outside OneDrive

```bash
mkdir -p ~/.venvs
python3 -m venv ~/.venvs/cypher
source ~/.venvs/cypher/bin/activate
pip install --upgrade pip
pip install -r /tmp/cypher_requirements.txt
```

If that errors on some package (Pillow / pdfplumber / pymupdf are the usual suspects), install them individually:

```bash
pip install "pdfplumber==0.9.0" "pymupdf>=1.23" "pytesseract>=0.3.10" \
            "Pillow>=9.0" "pandas>=2.0" "openpyxl>=3.1" "numpy>=1.24" \
            "jupyter>=1.0" "ipykernel>=6.0"
```

### 3. Verify imports work

```bash
~/.venvs/cypher/bin/python -c "
import pdfplumber, fitz, pytesseract, pandas, PIL
print('OK', pdfplumber.__version__, fitz.__version__, pandas.__version__)
"
```

You should get a single `OK 0.9.0 1.X.X 2.X.X`-style line within a second or two. If any line hangs or errors, fix that one package and re-test before continuing.

### 4. Smoke-test against the corpus

```bash
cd "/Users/danielburke/Library/CloudStorage/OneDrive-Personal/work/cypher"
~/.venvs/cypher/bin/python tools/triage.py \
    --input "/path/to/your/pdf/corpus" \
    --hint-sheet-type OCCM \
    --out research/results/triage_occm.csv
```

Expected: completes in a few minutes, no `TIMEOUT/ERR` messages (or very few — under 5). If you still see lots of timeouts, the PDFs themselves are cloud-only and need their own hydration pass. Run:

```bash
find "/path/to/your/pdf/corpus" \
    -name "*.pdf" -exec dd if={} of=/dev/null bs=1m status=none \; 2>&1 | tail -20
```

This reads every PDF byte-by-byte once, which forces OneDrive to hydrate them locally. Then re-run triage — should be timeout-free.

### 5. Register the new venv as the Jupyter kernel

So that `research/workbook.ipynb` picks up the new venv:

```bash
~/.venvs/cypher/bin/python -m ipykernel install --user --name cypher \
    --display-name "Python 3 (cypher)"
```

The old kernel (named `cypher` pointing at the OneDrive venv) gets overwritten — same name, new path.

### 6. Delete the old venv

Only after step 4 succeeds:

```bash
rm -rf "/Users/danielburke/Library/CloudStorage/OneDrive-Personal/work/cypher/.venv"
```

Frees ~500 MB of OneDrive storage and stops File Provider from trying to sync it.

### 7. Tell collaborators (yourself in three weeks)

Update `README.md` to point at `~/.venvs/cypher`. From now on:

- Activate: `source ~/.venvs/cypher/bin/activate`
- Or invoke directly: `~/.venvs/cypher/bin/python …`

## Scripts that may need updating

None of Cypher's source code hardcodes `.venv/bin/python` — the imports are relative to `PYTHONPATH`/`sys.path`. The only references are in `docs/TODO.md` and `marketing/launch_post*.md` example commands, which can stay (they show one valid pattern; users can use the new path).

If you previously created shell aliases or one-line copy-paste recipes that referenced `.venv/bin/python`, swap to `~/.venvs/cypher/bin/python`.

## What about the deploy?

Untouched. `deploy/_pymods/` is regenerated by `deploy/build.py` from the canonical sources — no venv assumption. Pyodide doesn't see the local venv at all. Migration is purely a local-development concern.

## Verification of success

After migration, when the next session runs:

- `triage.py` against `evalsp/` completes in **2–5 minutes** instead of 60+ minutes
- No `TIMEOUT/ERR` messages
- Notebook imports return immediately
- AMASIS / OASES / future parser smoke tests run to completion
